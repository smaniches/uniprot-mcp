# Hash-locked toolchain constraints

Every file in this directory is generated. Do not hand-edit a `.lock`.

## Why these exist

Workflows install their third-party toolchains with:

```
python -m pip install --require-hashes -r constraints/<name>.lock
```

Under `--require-hashes`, pip refuses to install any artifact whose SHA-256 is
not recorded in the lock. A substituted or backdoored wheel on the index
therefore cannot enter a CI, docs, release, or mutation-testing job, even if it
satisfies the version specifier.

The project itself is then installed with:

```
python -m pip install --no-build-isolation --no-deps -e .
```

Both flags are load-bearing, and `--no-deps` alone is **not** enough.
`--no-deps` skips the project's runtime dependencies, but PEP 517 build
isolation is a separate mechanism and stays on: pip would build a temporary
environment and download `hatchling` — `pyproject.toml`'s
`[build-system].requires` — straight from the index, outside `--require-hashes`,
and then execute it. `python -m build` isolates by default for the same reason,
which is why `release.yml` passes `--no-isolation`.

`constraints/build.in` closes that hole. It is compiled into every lock whose
workflow installs or builds the project, so the backend is hash-verified like
everything else and isolation can safely be switched off. With it in place the
install reaches the index for nothing at all — verified by running the same
command under `PIP_NO_INDEX=1`.

## The files

| File | Generated from | Consumed by |
| --- | --- | --- |
| `build.in` | hand-written (`hatchling`, `editables`) | compiled into `dev`, `test`, `docs`, `release` |
| `dev.lock` | `pyproject.toml` extras `test` + `dev`, `build.in` | `ci.yml` lint, `dev-lock-maintenance.yml` validate, `mutation.yml` |
| `test.lock` | `pyproject.toml` extra `test`, `build.in` | `ci.yml` test matrix, `integration.yml` |
| `docs.lock` | `pyproject.toml` extra `docs`, `build.in` | `docs.yml` |
| `release.lock` | `release.in` (`build`, `cyclonedx-bom`), `build.in` | `release.yml` |
| `mutation.lock` | `mutation.in` (`mutmut==2.5.1`) — **regenerated manually** | `mutation.yml` |
| `mutation-build.lock` | `mutation-build.in` (`setuptools`, `wheel`) | `mutation.yml`, maintenance validation |
| `uv-bootstrap.lock` | `uv.in` (`uv==0.11.20`) | `ci.yml` lock gate, `dev-lock-maintenance.yml` |

`mutation.lock` carries no project build backend by design: `mutation.yml`
always installs `dev.lock` alongside it, and that is where hatchling comes
from.

### Why mutation.lock is regenerated by hand

Every other lock is regenerated automatically — by the `ci.yml` `lock` gate on
every pull request, and by the monthly maintenance workflow. `mutation.lock` is
not, and that is deliberate.

`mutmut==2.5.1` and `glob2==0.7` publish **no wheels**. Resolving that graph
forces uv to *build* both sdists just to read their metadata, which executes
their `setup.py`. Doing that on every pull request would mean running arbitrary
third-party build code as a routine part of CI, and it would break the
maintenance workflow's upload-before-execution property.

So `scripts/regenerate-locks.sh` compiles with `--no-build`, which forbids
source builds outright, and `mutation.lock` moved to its own entry point:

```
scripts/regenerate-mutation-lock.sh
```

Run it deliberately — for a CVE in mutmut's graph, or after editing
`mutation.in` — and review the diff as you would a dependency bump from an
unfamiliar source. `--no-build` is a security control, not a tuning flag: if a
newly added dependency makes the routine compile fail, that dependency is
sdist-only and needs the same treatment rather than the flag being removed.

### Two different build backends

`build.in` and `mutation-build.in` solve the same class of problem at opposite
ends:

* **`build.in`** covers *this project's* backend. `pyproject.toml` declares
  `hatchling>=1.24`, so installing the local checkout needs hatchling.
* **`mutation-build.in`** covers *other people's* backends. `mutmut==2.5.1`
  and `glob2==0.7` publish no wheels, so pip builds both from source at
  install time, and hash-verifying an sdist does not help if the tool that
  compiles it is unverified.

  Which compiler pip uses depends on ambient environment state, which is the
  real problem. With `wheel` absent — the default in a fresh venv — pip takes
  the PEP 517 path, creates an isolated build environment, and downloads
  setuptools and wheel from the index outside `--require-hashes`
  (`Installing build dependencies` in the log, build reported as
  `Building wheel for glob2 (pyproject.toml)`). With `wheel` present it uses
  the legacy `setup.py bdist_wheel` path and whatever setuptools is already
  installed. Neither is a posture you want to depend on a runner image for.

  `mutation.yml` therefore installs `mutation-build.lock` first and passes
  `--no-build-isolation`, which pins the build tools on every runner.

Both cases need `--no-build-isolation`, because `--require-hashes` and
`--no-deps` govern *which distributions* are installed, never *how* they are
built.

`uv-bootstrap.lock` is the root of trust: it installs the exact `uv` that
compiles every other lock, which is what makes regeneration byte-reproducible.
Bump `uv.in` deliberately, in its own reviewable commit.

## Regenerating

```
python -m pip install --require-hashes -r constraints/uv-bootstrap.lock
scripts/regenerate-locks.sh              # reuse committed pins as preferences
scripts/regenerate-locks.sh --upgrade    # advance to newest allowed by ranges
```

That covers every lock except `mutation.lock`, which has its own deliberate
entry point for the reason described above:

```
scripts/regenerate-mutation-lock.sh              # reuse committed pins
scripts/regenerate-mutation-lock.sh --upgrade    # advance transitives
```

`--upgrade` is not recorded in the generated headers, so a refreshed lock stays
byte-identical to what the CI `lock` gate regenerates without it. That gate runs
`scripts/regenerate-locks.sh` and then `git diff --exit-code constraints/`, so
CI fails if a lock is stale relative to its inputs.

The script compiles with an explicit `--python-version 3.11`, the project's
`requires-python` floor. This is load-bearing: without it uv resolves against
whatever interpreter is running and that overrides `requires-python`, so
compiling on 3.12 drops the cp311 wheel hashes and the sync gate fails against
a lock generated on 3.11. Keep the target at the floor so the resolution stays
as wide as `requires-python` allows, and move it only when that floor moves.

`.github/workflows/dev-lock-maintenance.yml` runs the `--upgrade` form monthly
and opens a single PR with the result.

## Dependabot

`.github/dependabot.yml` excludes `constraints/**`. Dependabot's pip parser
cannot tell a transitive pin from a direct dependency in a compiled lock, so it
would otherwise open PRs that bump transitives and break the sync gate.
Transitive updates arrive through the monthly maintenance workflow instead;
for an urgent CVE, dispatch that workflow manually.
